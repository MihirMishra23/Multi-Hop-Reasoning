1. ✅ Ray init, FSDP shard of Qwen3-1.7B on 4 GPUs

   CUDA graphs captured (~3-30 s depending on `enforce_eager`)
3. ❌ verl calls `release_memory_occupation` → 3× Connection error →
   `RuntimeError: Failed to complete async request to release_memory_occupation

of a working server. Same failure with and without `enforce_eager=True`.

## Plans for the morning

### Plan B (recommended): switch rollout backend from sglang → vllm

verl 0.7 supports `actor_rollout_ref.rollout.name=vllm` with multi-turn tool
calling. vllm 0.10 worked fine in our standalone Qwen3 sanity check. Avoids the
sglang+Blackwell hybrid-engine bug entirely.

Steps (rough):
1. `pip install vllm==0.10.2 --no-deps` into `searchr1-sgl` (currently
   removed; deps will mostly already be present).
2. In `run_qwen3_1.7b_search_multiturn.sh` change `rollout.name=sglang` → `vllm`,
   drop the `engine_kwargs.sglang.attention_backend` flag, add
   `engine_kwargs.vllm` block if needed.
3. Verify verl's `search_tool` works with vllm rollout. Upstream docs only show
   sglang for this recipe, so this is the main unknown — may need to switch to
   the vllm-flavored multi-turn config (look for `examples/ppo_trainer/...`
   with multi_turn).
4. If `search_tool` doesn't have a vllm path: open a small shim in
   `verl/tools/search_tool.py` and/or use verl's async vllm server adapter.

### Plan C: downgrade verl to a version pinned at sglang ≥ 0.5.10

verl HEAD at github.com/verl-project/verl recently bumped sglang. The Search-R1
recipe files might still be in tree. Risk: bigger surface to retest.

### Plan D: switch from hybrid engine → standalone sglang servers

verl 0.7 has a `RolloutMode.STANDALONE` path (saw it in
`async_sglang_server.py:249`: `logger.info("skip sleep in standalone mode")`).
That mode skips the broken `release_memory_occupation`. Cost: rollout GPUs are
separate from training GPUs — needs more GPUs than we have (4) per node.

## Debug fork (only if Plan B fails)

The `release_memory_occupation` Connection error originates HTTP-side, not
timeout. To diagnose:

- Capture sglang HTTP server stderr — set env `SGLANG_LOG_LEVEL=DEBUG` and
  redirect each sglang subprocess's stdout. The current log mixes everything
  via Ray and the actual sglang Python traceback is being swallowed.
- Check whether `gpu_memory_utilization=0.5` is too high and the FSDP weights
  collide with sglang's reservation, causing OOM on the implicit weight gather
  inside `release_memory_occupation`. Try 0.3.
- Smoke test sglang outside verl with `--enable-memory-saver`,
  `--attention-backend flashinfer`, then call `/release_memory_occupation`
  directly via curl. If that crashes too → upstream sglang bug, escalate.
